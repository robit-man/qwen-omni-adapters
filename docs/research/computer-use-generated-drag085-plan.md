# 085: Generated drags must reach the existing guarded native boundary

## Failing criterion and evidence

An operation advertised to the generated-task planner as supported by a current
native control must have an executable generated-task route. Existing public
same-scope drag/drop support must remain available in the autonomous desktop
loop. This does not mean every proposed drag is useful or eligible for input.

The frozen084 actual pair returned two real Ornith replies. A failed expansion;
B passed its null-intent legacy schema and canonical validation, but chose a
Workbench-window drag into Firefox for a read-brief objective. Independent grade:
2/2 own-schema,1/2 canonical,0/2 useful, whole-stage prerequisite false.
No GUI input occurred. Preserve the raw replies and the negative grade.

Source tracing reveals an additional execution mismatch. Generated `ui` plans
use `verified_prefix`, which calls `ComputerUseStore.immediate_transition`.
`compile_immediate_transition` returns `requires_replan` for every drag_drop;
the private boundary parser also excludes that verb. Consequently even a useful,
fresh same-scope drag that the existing native executor supports is impossible
through this generated path. Public workflows already check both endpoints and
reject cross-scope, missing, stale, hidden, sensitive or geometrically invalid
destinations. B would fail these lower guards too; canonical admission was not
a demonstrated dispatch or verification bypass.

## One bounded hypothesis

Treat an already-supported native drag as one guarded input followed by a fresh
observation, using the existing observation-boundary machinery. Do not invent
a universal effect for dragging, use model prose as an oracle, accept an
already-visible label as proof of acquisition, or execute a suffix before
replanning from the observed result. Preserve the current endpoint and ownership
guards. This repairs an execution capability gap; it does not repair B's wrong
resource/target semantics or establish whole-task success.

## Acceptance and execution order

1. Independent preregistration and a reviewed source-linked proposal precede
   implementation. The fresh source baseline must pass unchanged.
2. A previously rejected, supported same-scope generated drag reaches exactly
   one existing native input offer and returns a fresh observation with unknown
   effect and zero verified progress. The model's `expect` and terminal prose
   must not become acquisition or completion proof.
3. A generated multi-step prefix stops at the drag boundary; following typing,
   saving or submission remains unexecuted until a later planning phase.
4. Public verified workflows preserve their explicit predicate semantics. Other
   verbs and existing pointer/keyboard/text/selection behavior remain unchanged.
5. Cross-scope, missing, changed, hidden, protected or stale destinations and
   denied/cancelled input produce no new dispatch. Ambiguous or invalid input
   is not repaired in place, and uncertain previous input is not replayed.
6. Validate schema/parser/effect/route agreement and source-bound before/after
   receipts. Do not mistake a synthetic provider test for physical desktop proof.
7. Freeze the source, run relevant focused checks, independent controls and the
   full repository gate. Preserve failures rather than restarting blindly.
8. Only after those pass, prepare one bounded actual native acceptance using the
   real Ornith GPU1 stack, current native applications and actual pointer input,
   with evaluator-owned setup and independent artifact/effect observation. The
   live method, criterion and ownership cleanup must be frozen before execution;
   no response injection, preferred-target coaching, resampling or forced point.
   CUDA worker changes are unnecessary. Fresh broker/profile/lease/residency,
   idle/default-ledger admission and unrelated-window preservation remain required.
